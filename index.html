Replication that only existed on paper

<!-- 2026 · kafka high availability -->

A government email platform (~10k notifications a day) ran three Kafka brokers for redundancy. All three were containers on one host. When that host's disk filled up they died together and email stopped for 10 hours. I planned and executed the move to three separate hosts alone, in a 16-minute window, with zero messages lost.

  • Chose lift-and-shift over a fresh cluster: moved each broker's data directory intact, so identities, offsets and topics carried over with no partition reassignment.
  • Repointed the KRaft quorum and advertised listeners from container hostnames to real IPs, the only change brokers on different machines actually needed.
  • The upstream app has no retry and drops the payload on failure, so I built a stand-in HTTP service on the same port that persisted every request to disk before answering 200, then replayed them after cutover. Tested against the real client code, including 20 MB attachments and 40 concurrent requests, and rehearsed on a spare port days earlier.
  • Wrote the runbook with a rollback decision rule and a troubleshooting section per failure point, so 22:00 did not depend on improvisation.
  • Mid-preparation, found production had silently stopped sending for 2 hours: a hung SMTP socket with no timeout had stalled the single consumer with 3,200 emails queued. Killed just that socket; delivery resumed in under a second without a restart.

16 minutes of downtime, 13 in-flight emails captured, 13 replayed, 0 lost. I then stopped a broker on purpose: the cluster kept its leader, kept delivering, and returned to full replication when it came back.

Cross-agency publication pipeline with per-document payments

<!-- 2026 · cross-agency integration -->

Every application the client approves has to be forwarded to a second agency for publication, with a state fee (PNBP) collected per document. The two systems had never exchanged data automatically. I built the integration end to end.

  • Intake payload with a PNBP payment voucher per document; NPWP/NIK validated before send so the counterpart never sees a 422.
  • Bulk callback endpoint that matches on transaction id and file id; idempotent migrations; uniqueness moved to the file id.
  • Elasticsearch audit trail at all three integration boundaries, with a DB fallback when ELK is unavailable and configurable retry/connect timeouts.
  • Error taxonomy: 400/413/422 are terminal, everything else retries; a backfill command that survives one broken transaction and writes its own summary.
  • Diagnosed a callback "timeout" reported by the counterpart when data had actually landed: an output-buffer release loop plus an ELK 400. Fixed both.

Approved applications now flow to the partner agency without manual handling, and applicants see payment status per document in their inbox.

Name search that survived a nationwide launch

<!-- 2025 · search under load -->

When a nationwide government programme launched, thousands of organisations registered through one application at once. Name-similarity checks ran MATCH AGAINST in MariaDB and then looped Levenshtein distances in PHP 5.6: fine at normal load, fatal at 1,000+ concurrent requests. The application went down.

  • Moved the name search to Elasticsearch on the application side; full-text and fuzzy matching under concurrency is what it's built for.
  • A colleague built the CDC pipeline (Debezium -> RisingWave) so existing data stayed in sync without manual reindexing.

No more outages on registration spikes; the database stopped being the bottleneck for name checks.

Async email delivery around a host that couldn't install anything

<!-- 2025-2026 · async messaging -->

The core application runs Yii1 on FreeBSD where the package manager no longer works, and Yii1 predates Composer, so a Kafka client could not go in. Synchronous email sends were blocking core transactions at peak.

  • Designed a standalone, stateless Java service: the application does one multipart HTTP POST, the service publishes to Kafka, a consumer delivers through SendGrid.
  • Three-tier dead-letter topology (DLT1 -> DLT2 -> DLT3) with different retry schedules; offsets committed only after successful delivery.
  • Java 21 virtual threads keep concurrency high without a large thread pool; no database, so it scales horizontally.

The application sends email through Kafka without touching its own runtime, and sibling applications with the same constraints reuse the service.

A partner-facing lookup API that stopped taking down the warehouse

<!-- 2026 · lakehouse api -->

An endpoint that lets partner institutions search transactions by the two parties' names was running unbounded queries and pushing the StarRocks backend out of memory.

<!-- 2025-2026 · production -->
